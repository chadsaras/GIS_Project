2026-10-01 (7)  Earth Engine download bug found and fixed
------------------------------------------------------------------------------
  - First full run (--tile 32 --workers 8) finished 0 GSED blocks in 14.5 min; job killed.
  - Cause (from a timing test): every request failed with "Too many input pixels per output
    pixel. Need 38155, but only 16384 allowed." gsed_image/worldcover_image used
    reduceResolution(maxPixels=16384); GSED's native UTM tiles are skewed against EPSG:31983,
    so EE needs ~38k 10 m pixels per 1 km cell. Block size was not the problem.
  - Second bug: after the first failed tile, the thread pool still ran every queued tile
    (each retrying ~75 s) before exiting, so the job looked alive but did nothing.
  ~ gee.py: maxPixels=65536 (EE's cap, as PLAN 2.3 says) for GSED and WorldCover; the download
    stops at the first failed tile; every failed attempt is logged. 05_export_gee.py flushes
    its progress lines.
  - Next: pull on gpu77, rerun the timing test, then restart the full download.

Gotcha (for anyone re-authenticating)
  On the Google permission screen tick "Select all". With earthengine-api 1.7.46, leaving any
  box unticked saves a login that Google later rejects (RefreshError invalid_scope), and ee only
  says "Please authorize access ... run earthengine authenticate". Fix: earthengine authenticate
  --auth_mode=notebook --force, tick all. Credentials live in ~/.config/earthengine/credentials
  on the server: never copy them into the repo.

Finding
  On the synthetic test, "sum" pooling fit badly (R2 -0.53) while "logsum" fit well (R2 0.66).
  Real municipalities differ by up to 10,000x in cell count, so expect logsum to win
